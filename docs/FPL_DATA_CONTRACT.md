# FPL player-data contract

## Evidence snapshot

The candidate official endpoint was requested live at `2026-08-17T11:32:17.936Z`:

```text
GET https://draft.premierleague.com/api/bootstrap-static
HTTP 200
Content-Type: application/json
```

The response contained these relevant top-level collections:

- `elements`: 587 player records
- `teams`: 20 club mapping records
- `element_types`: four position mapping records

All 587 live player records had unique positive integer IDs, valid team references, valid position references, and a unique positive integer `draft_rank` from 1 through 587. The position totals were 65 goalkeepers, 193 defenders, 259 midfielders, and 70 forwards. No live record was rejected or skipped during verification.

This snapshot is evidence about one response, not a stability guarantee. The endpoint and schema are undocumented or insufficiently documented and may change without notice.

## Project response

`GET /api/fpl` returns a project-owned contract:

```ts
interface FplPlayerDataResponse {
  retrievedAt: string
  playerCount: number
  players: Player[]
}
```

`retrievedAt` is generated by this project after successful normalization. `playerCount` is computed from the normalized array. Neither field comes from the upstream response. The endpoint returns `Cache-Control: no-store` and never returns the complete raw bootstrap payload.

## Verified field mapping

| Upstream field and location | Normalized field | Expected upstream type / nullability | Meaning and evidence |
| --- | --- | --- | --- |
| `elements[].id` | `Player.id` | Positive safe integer; required and non-null | **Verified fact:** unique for all 587 observed records. **Project decision:** convert to a string so upstream numeric types do not spread through the domain. The API does not formally guarantee cross-season identity stability. |
| `elements[].web_name` | `Player.displayName` | Non-empty string; required and non-null | **Verified fact:** present on all observed records and contained concise player labels. **Uncertainty:** its display semantics are inferred from the field name and values, not formal endpoint documentation. |
| `elements[].element_type` → `element_types[].id` → `element_types[].singular_name_short` | `Player.position` | Positive integer reference plus non-empty string mapping; required and non-null | **Verified fact:** observed mappings were `GKP`, `DEF`, `MID`, and `FWD`. **Project decision:** explicitly map `GKP` to domain `GK`; the other three map directly. Unknown labels or references are errors. |
| `elements[].team` → `teams[].id` | `Player.club.id` | Positive integer reference; required and non-null | **Verified fact:** all observed references resolved to one of 20 unique team IDs. **Project decision:** convert the referenced ID to a project-owned string. |
| `teams[].name` | `Player.club.name` | Non-empty string; required and non-null | **Verified fact:** present and unique for all 20 observed teams; used as the upstream club name. |

## Position mapping

The live `element_types` collection supplied the mapping keys. Production code does not hard-code position IDs or clubs.

| Observed upstream short name | Domain position |
| --- | --- |
| `GKP` | `GK` |
| `DEF` | `DEF` |
| `MID` | `MID` |
| `FWD` | `FWD` |

An unknown upstream label fails with `MISSING_REQUIRED_MAPPING`. A player that references an absent position or club fails with `INVALID_PLAYER`. No unknown value is silently converted to a valid domain position or club.

## Deliberately omitted fields

The live response contained `status` values `a`, `i`, `d`, `u`, and `s`, along with fields such as `news` and `chance_of_playing_next_round`. The response did not define those codes, and 480 of 587 next-round chance values were null. Availability is therefore not normalized in Phase 2.

Official-looking statistics such as `total_points`, `form`, `points_per_game`, goals, assists, clean sheets, and other metrics were also present. Their season context and precise semantics were not established from the response, so they are omitted rather than mislabeled. No projection is created.

## Validation and failure behavior

The client and normalizer classify controlled failures:

- `NETWORK_ERROR`: the upstream request could not be completed.
- `UPSTREAM_HTTP_ERROR`: the endpoint returned a non-success status.
- `UNEXPECTED_CONTENT_TYPE`: a successful response was not identified as JSON.
- `INVALID_JSON`: the response body could not be parsed.
- `UNEXPECTED_SCHEMA`: required top-level collections were absent or had the wrong shape.
- `MISSING_REQUIRED_MAPPING`: club or position mapping data was malformed, duplicated, or unknown.
- `INVALID_PLAYER`: a required player field was invalid, an ID was duplicated, a reference was unresolved, or a non-null rank was invalid.

Normalization is strict and fail-fast. An invalid record causes the complete request to fail rather than returning a silently incomplete player pool. `/api/fpl` converts expected integration failures to HTTP 502 with a project-owned error code and a generic public message; unexpected internal failures return HTTP 500.

## Testing boundary

Committed fixtures are tiny, fictional, and derived only from the verified shape. Deterministic unit and CI tests never contact the Premier League endpoint. `npm run verify:fpl-live` is a separate opt-in network check and is intentionally excluded from GitHub Actions.
